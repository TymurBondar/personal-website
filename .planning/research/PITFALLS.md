# Pitfalls Research

**Domain:** Personal portfolio website modernization (Next.js 14, removing DaisyUI, adding CI/CD)
**Researched:** 2026-03-02
**Confidence:** MEDIUM — findings verified across multiple sources; some DaisyUI-removal specifics are MEDIUM because official docs don't cover "removal" scenarios explicitly

## Critical Pitfalls

### Pitfall 1: DaisyUI CSS Variables Left Behind in globals.css

**What goes wrong:**
After removing DaisyUI from `tailwind.config.js`, the existing `globals.css` still contains references to DaisyUI's CSS variable system (`--b1`, `--b2`, `--p`, `--s`, etc.). The existing code also uses `bg-base-100`, `bg-base-300`, `bg-base-200` class names throughout the codebase (Navbar, layout.js). Without DaisyUI, these classes resolve to nothing — the background becomes transparent or inherits wrong colors.

**Why it happens:**
DaisyUI injects an entire theming layer via CSS variables. Removing the plugin doesn't automatically remove references to those variables in markup. Developers often remove the plugin, delete the `daisyui` config block, and assume the cleanup is complete — but the class names and variable references remain scattered throughout components.

**How to avoid:**
1. Audit every DaisyUI class name in the codebase before removing the plugin. Current inventory: `navbar`, `navbar-start`, `navbar-end`, `btn`, `btn-ghost`, `dropdown`, `dropdown-end`, `dropdown-content`, `menu`, `menu-sm`, `menu-horizontal`, `rounded-box`, `hero`, `hero-content`, `timeline`, `timeline-snap-icon`, `timeline-compact`, `timeline-vertical`, `timeline-middle`, `timeline-start`, `timeline-end`, `bg-base-100`, `bg-base-300`, `bg-base-200`, `text-success`, `text-accent`.
2. Replace every DaisyUI class with explicit Tailwind utilities before removing the plugin — not after. Keep DaisyUI installed until all replacements are done.
3. Remove the plugin from `tailwind.config.js` only as the final step, after a full visual check.

**Warning signs:**
- Invisible backgrounds (transparent where color was expected)
- Missing button styles — buttons appear as plain unstyled text
- Navbar collapses to default browser styling
- Layout shift from zero-height containers

**Phase to address:** DaisyUI removal phase — must be the first task, before any styling work begins.

### Pitfall 2: Semantic DaisyUI Class Names Not Replaced Consistently

**What goes wrong:**
The Navbar component uses DaisyUI's interactive components: `dropdown`, `dropdown-end`, `dropdown-content`, `menu-sm`. These are not just styling classes — DaisyUI uses CSS-only interactions (`:focus-within`, `tabIndex` tricks) that won't work once the plugin is removed. The mobile dropdown menu will stop functioning entirely since it relies on DaisyUI's focus-based visibility toggle.

**Why it happens:**
Developers focus on visual styles (colors, spacing) and overlook that component library classes encode behavior through CSS selectors, not just appearance.

**How to avoid:**
The Navbar mobile dropdown must be rebuilt with React state (`useState` + click handler + outside-click listener) when DaisyUI is removed. Plan this as a distinct task, not an afterthought. The desktop nav (`hidden sm:flex`) is straightforward and only needs visual re-styling.

**Warning signs:**
- Mobile menu button appears but clicking does nothing
- Dropdown appears permanently open on mobile
- Keyboard navigation breaks on the nav

**Phase to address:** DaisyUI removal phase — rebuild Navbar mobile menu with React state immediately after removing the plugin.

### Pitfall 3: Stale Metadata Tanking SEO and Social Previews

**What goes wrong:**
The current `layout.js` has `description: "Generated by create next app"`. When the refreshed site is shared on LinkedIn (the primary professional platform for a software engineer), the social preview shows "Generated by create next app" — undermining the professional impression the portfolio is meant to create. Beyond social sharing, thin or boilerplate metadata hurts discoverability.

**Why it happens:**
Metadata is invisible during development. It's easy to update content on the page without touching the metadata export. Developers often ship "good enough" metadata from the template and never return to it.

**How to avoid:**
- Set `metadataBase` in root `layout.js` to the production Vercel URL — without this, Open Graph images are relative URLs that social crawlers cannot resolve.
- Write unique `title` and `description` for each page (home, about, projects). Each should reflect the actual page content — not the site title repeated.
- Test social previews using [opengraph.xyz](https://www.opengraph.xyz) or the LinkedIn post inspector before considering metadata done.

**Warning signs:**
- LinkedIn share shows "Generated by create next app"
- Google Search Console shows duplicate title tags across pages
- No profile photo or meaningful image when pasting URL on Slack/Discord

**Phase to address:** Content update phase — metadata should be updated at the same time as page content, not separately.

### Pitfall 4: Outdated Content Eroding Professional Credibility

**What goes wrong:**
The homepage currently says "New York BASED" and the About page references "soon after moving to NYC." The actual situation is Toronto, Purdue University (online), Spelling Bee of Canada internship, and IT & Digital Marketing Specialist role. Visitors who check the site after meeting Tymur at an event or through LinkedIn will immediately notice the disconnect. Hiring managers treat stale portfolios as a signal of low attention to detail.

**Why it happens:**
Content updates feel less urgent than visual work, so developers prioritize the redesign and defer content — then forget to update it.

**How to avoid:**
Update all content before starting any visual work. Treat the content audit as Phase 1, not a final polish step. Specific items to update:
- Location: New York → Toronto, Canada
- University: Binghamton University → Purdue University (online)
- Timeline: add Spelling Bee of Canada internship
- Timeline: add IT & Digital Marketing Specialist role
- Remove "Currently" ambiguity in the timeline — it now means something specific

**Warning signs:**
- Any page mentions "New York" or "NYC"
- Any reference to Binghamton University
- Timeline ends without the 2025 internship and current role

**Phase to address:** Content update phase — update before visual work begins.

### Pitfall 5: 21st.dev Component Styling Conflicts with Custom Tailwind

**What goes wrong:**
21st.dev components are typically built with Tailwind and shadcn conventions, using CSS variables for theming (`--background`, `--foreground`, `--primary`, etc.). If the rest of the site uses raw Tailwind color classes (like `bg-zinc-900`, `text-white`) without defining matching CSS variables, the hero component will have a different visual language — different border radii, different shadows, different spacing rhythms — creating an inconsistent look.

**Why it happens:**
Component libraries assume a specific CSS variable setup that matches their design token system. When integrating a single component in isolation, developers often don't set up the matching variable layer, leaving the component styled differently than the surrounding content.

**How to avoid:**
Before integrating the 21st.dev hero component:
1. Identify which CSS variables the component uses (inspect source or readme).
2. Define those variables in `globals.css` `:root` block, mapped to the site's chosen color palette.
3. Verify the component respects your color choices before doing any other page styling.

**Warning signs:**
- Hero component has different font size scale or letter spacing than the rest of the site
- Border radius on hero doesn't match site-wide radius choices
- Hero background color doesn't match the page background color

**Phase to address:** Styling phase — resolve design token alignment when integrating the hero component.

## Technical Debt Patterns

Shortcuts that seem reasonable but create long-term problems.

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| Keep DaisyUI classes as inline `style` overrides | Faster migration | CSS specificity wars, utility classes won't override, debugging nightmare | Never — replace classes properly |
| Copy raw `<img>` tags from DaisyUI examples | Faster markup | No lazy loading, no format optimization (WebP), CLS layout shift on hero image | Never — always use `next/image` |
| Skip `metadataBase` and test locally | Works in dev | OG images break as relative URLs in production, social shares show no image | Never — set metadataBase from day one |
| Use `!important` to override conflicting styles | "Fixes" specificity instantly | Makes every future style change harder, cascading maintenance debt | Never for this project — use `@layer` instead |
| Leave `description: "Generated by create next app"` | No work needed | Kills first impressions on LinkedIn/social shares | Never |
| Put all styles in globals.css | Simple, one file | Unscoped global styles bleed across components, hard to maintain | Only for true global tokens (colors, fonts) |

## Integration Gotchas

Common mistakes when connecting to external services.

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|------------------|
| Vercel + GitHub Actions | Forgetting to add `VERCEL_TOKEN`, `VERCEL_ORG_ID`, `VERCEL_PROJECT_ID` as GitHub repository secrets | Add all three secrets before merging the first workflow file; get IDs from `.vercel/project.json` after running `vercel link` |
| GitHub Actions lint job | Using `next build` to catch lint errors — it silently swallows lint output before the actual error surfaces | Run `next lint` as a separate dedicated step before the build step |
| Vercel auto-deploy | Running a custom GitHub Actions pipeline alongside Vercel's zero-config Git integration — both deploy simultaneously, causing double deploys | Either use Vercel's native Git integration OR GitHub Actions, not both. Disable Vercel's automatic Git integration if using GitHub Actions |
| Google Search Console | Forgetting to submit sitemap after deploying the refreshed site | After first production deploy, submit `/sitemap.xml` to Google Search Console |

## Performance Traps

Patterns that work at small scale but fail as usage grows (or hurt Core Web Vitals immediately).

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| Raw `<img>` instead of `next/image` for the hero photo | Hero image downloads full size on mobile (275px display, 3MB+ download) | Use `<Image>` from `next/image`, set `priority={true}` on hero | Immediate — hurts LCP on all devices |
| Missing `width` and `height` on `<Image>` | Page jumps when hero loads (CLS layout shift) — penalizes Core Web Vitals | Always specify explicit `width` and `height` or use `fill` with a sized container | Immediate — visible on every page load |
| Unscoped global CSS | A style intended for one page bleeds into all pages, causing visual bugs that are hard to trace | Keep globals.css only for true global tokens; use component-scoped classes via Tailwind | At 5+ pages — grows harder to debug as site expands |
| Missing `robots.txt` and `sitemap.xml` | Google crawls the site but doesn't index pages, or indexes the wrong ones | Add `src/app/robots.ts` and `src/app/sitemap.ts` — Next.js auto-serves them at the correct paths | Immediately affects indexability |

## UX Pitfalls

Common user experience mistakes for a software engineer portfolio.

| Pitfall | User Impact | Better Approach |
|---------|-------------|-----------------|
| No contact information visible above the fold | A recruiter visits the home page and doesn't know how to reach you without scrolling or navigating | Put at minimum an email link or LinkedIn in the hero section, not only in the footer |
| Vague project descriptions ("Used React and Node to build...") | Reader finishes the description with no understanding of what problem was solved | Lead with outcome: "Built X for Y, which resulted in Z" — describe the problem first |
| Too many projects shown (showing everything) | Dilutes the signal — weaker projects make stronger ones look worse by comparison | Show 2–4 projects max; prioritize projects with real users or measurable outcomes |
| Generic hero text ("passionate developer who loves solving problems") | Indistinguishable from 1000 other portfolios; a recruiter won't remember you | Use specific, personal language: name + role + location + what you're focused on |
| No visual hierarchy on About/timeline page | Visitor doesn't know what to look at first; timeline entries blur together | Establish clear typographic hierarchy: date is secondary, role title is primary, description is supporting |
| Navigation items don't reflect actual pages ("About Me" vs "About") | Minor, but inconsistent labeling signals lack of attention to detail | Keep nav labels short, consistent, and matching the page heading |

## "Looks Done But Isn't" Checklist

Things that appear complete but are missing critical pieces.

- [ ] **DaisyUI removal:** Visually looks fine on desktop — verify mobile dropdown still works (requires React state, not DaisyUI focus trick)
- [ ] **Content update:** Homepage updated — verify About page timeline also updated (separate file: `src/app/about/page.js`)
- [ ] **Metadata:** Title shows correctly in browser tab — verify Open Graph tags by pasting URL into LinkedIn post inspector or `opengraph.xyz`
- [ ] **CI/CD:** Lint workflow exists — verify it actually runs on push by checking the Actions tab after a test commit
- [ ] **Vercel deploy:** Deploys on push to main — verify both Vercel's Git integration and GitHub Actions aren't both running simultaneously (double-deploy)
- [ ] **Image optimization:** Hero image displays correctly — verify there's no CLS by running Lighthouse or checking Core Web Vitals in Vercel Analytics
- [ ] **Mobile nav:** Hamburger menu appears on small screens — verify it opens and closes correctly by testing on an actual phone (not just browser resize)
- [ ] **21st.dev hero:** Component renders visually — verify CSS variables are defined and the component matches the surrounding color palette

## Recovery Strategies

When pitfalls occur despite prevention, how to recover.

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| DaisyUI classes left in markup after plugin removal | MEDIUM — tedious but mechanical | Grep for remaining DaisyUI class names, replace one component at a time; re-add DaisyUI temporarily if visual reference is needed |
| Mobile nav broken after DaisyUI removal | LOW — isolated component | Add `useState` to Navbar, add click handler to hamburger button, add `display: none/block` conditional on state |
| Metadata never updated, shipped to production | LOW — quick fix | Update `metadata` export in `layout.js` and each page's `page.js`; redeploy; re-submit sitemap to Search Console |
| Double-deploy (both Vercel Git integration and GitHub Actions running) | LOW | Disable Vercel's automatic deployment in Vercel project settings → Git → turn off auto-deploy |
| 21st.dev component looks visually inconsistent | LOW–MEDIUM | Inspect component's required CSS variables, define them in `globals.css`, align with site color tokens |
| Hero image causing CLS | LOW | Add explicit `width` and `height` props to `<Image>` component |
